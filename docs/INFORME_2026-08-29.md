## 1. Confirmación de D-49 — autenticación propia, sin Supabase Auth

**Renaser OS emite y valida su propia identidad** (sesión opaca en Redis vía Spring Session +
cookie/header `HttpOnly`). Es decisión del dueño del proyecto (2026-08-26), tomada contra la
recomendación técnica previa (D-9/D-18: mantener Supabase Auth) y sostenida después de exponerle
el costo. El login social (Google/Apple/Facebook) también dejó de delegar en Supabase: el
intercambio OAuth lo hace el propio backend Java (D-18 superada).

**Se detectó y quedó anotado:** el `CLAUDE.md` raíz del repo (§5.3.1, §6, §11) seguía diciendo
*"Auth se queda en Supabase"* — quedó desactualizado por D-49 y contradice `docs/MODULO_AUTH.md`,
que es la fuente vigente. Pendiente de corregir por la propia regla 0.4 del proyecto ("los
documentos no pueden contradecirse") — no se tocó en esta sesión porque no fue lo pedido, se deja
anotado para la próxima vez que se edite ese documento.

**Estado real verificado contra código** (no solo contra la tabla de fases de §9 del doc, que
tiene una celda desactualizada — fase 2 figura "en curso" pero fases 5/6/7 ya están hechas):

| Fase | Estado real |
|---|---|
| Credencial + `PasswordEncoder` + Spring Session | ✅ Hecho |
| Migraciones `V2`/`V3`, puertos | ✅ Hecho |
| Login social Google/Apple/Facebook (adaptadores + compositor + `IdentidadExterna`) | ✅ Hecho |
| Reset de contraseña | ✅ Hecho (envío de correo con adaptador `NoOp`, sin proveedor real) |
| **Exigir la sesión** (`authenticated()` + CSRF) | ❌ **Sin empezar** — `SecurityConfig` sigue en `anyRequest().permitAll()` con CSRF deshabilitado, a propósito |
| Migración de `X-Actor-Id` (162 usos / 54 controllers) | ❌ Sin empezar — depende de lo anterior |

**Por qué no se activó CSRF/`authenticated()` en esta sesión:** el propio código lo advierte
(`SecurityConfig.java`, comentario en `apiFilterChain`): activarlo ahora dejaría a toda la API
respondiendo 401 de golpe, porque no está confirmado que la app React Native ya mande el header
de sesión (`X-Auth-Token`) en cada request (pregunta abierta A-3 del documento). Queda pendiente
de una confirmación explícita antes de tocarlo.

## 2. Limpieza — variable de Supabase retirada de `application.yaml`

Se eliminó el bloque:

```yaml
security:
  oauth2:
    resourceserver:
      jwt:
        jwk-set-uri: ${SUPABASE_JWKS_URL:https://apvnaigldsjqeloiolcu.supabase.co/auth/v1/.well-known/jwks.json}
```

Verificado antes de sacarlo que nada lo usaba: `SecurityConfig` no arma un
`.oauth2ResourceServer(...)` en su cadena de filtros (usa sesión propia, no JWT propio), y los
decoders de Google/Apple (`GoogleJwtDecoderConfig`, `AppleJwtDecoderConfig`) declaran su propio
bean `JwtDecoder` calificado con `@Qualifier`, con su propio JWKS URI hardcodeado — no dependen
del autoconfigurado por Boot a partir de esa property. Los 18 tests de esos dos adaptadores
(`GoogleIdentidadAdapterTest`, `AppleIdentidadAdapterTest`) pasan igual tras el cambio.

## 3. Revisión de autorización en `AccountRequest` (solicitudes de alta)

Se pidió restringir el `POST` de aprobar solicitudes a ADMIN/ALCHEMIST. **Ya estaba hecho, no
hizo falta construir nada:**

- `AccountRequest.approve()`/`reject()` (dominio) llaman `requireManager(actor)` →
  `actor.canManageRoles()` → si el actor no es ADMIN/ALCHEMIST, lanza
  `NotAuthorizedException("Solo ADMIN/ALCHEMIST deciden solicitudes de alta")`.
- `GlobalExceptionHandler` mapea esa excepción a **403**.
- Test de autorización negativa ya existe: `AccountRequestTest` → *"un TRAINEE no puede aprobar
  solicitudes"* (cumple CLAUDE.md §0.3).
- Actor `SUSPENDED` también cubierto: `AccountRequestServiceTest.approveRechazaActorSuspendido`.

Lo único pendiente ahí (bloqueado, no es trabajo de esta sesión): mover el chequeo del dominio a
`@RequiresPermission` + `AccessGuard` a nivel controller — bloqueado por R-2 (falta definir la
matriz de permisos de `MENTOR_LEAD`). Mientras tanto la regla de negocio ya se aplica y está
probada, un nivel más adentro de lo que el patrón final pide.
