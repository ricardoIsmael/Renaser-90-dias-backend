Severidad: Alta. Fuente: `docs/informes/auditoria-seguridad-concurrencia-2026-09-01.html`.

## Qué estaba mal

Dos problemas distintos, ambos en el flujo `POST /api/v1/onboarding/v90-recordings/{id}/validation`.

### 1. Doble arranque de validación

`GrabacionV90Service.solicitarValidacion` (antes del fix, `src/main/java/.../onboarding/application/services/GrabacionV90Service.java:72-80`):

```java
@Override
@Transactional
public void solicitarValidacion(SolicitarValidacionV90Command command) {
    requireActorActivo(command.usuarioId());
    GrabacionV90 grabacion = requireGrabacionPropia(command.usuarioId(), command.grabacionId());
    grabacion.procesarIntentoDeValidacion(clock);
    saveGrabacionPort.guardar(grabacion);
    despacharDespuesDelCommit(command.usuarioId(), command.grabacionId());
}
```

`requireGrabacionPropia` (línea ~109-116) leía con `loadGrabacionPort.porId(grabacionId)`, **sin
ningún bloqueo**. `GrabacionV90.procesarIntentoDeValidacion()` tiene un guard en memoria (ver
`GrabacionV90.java:108-124`, agregado para E-37) que rechaza un segundo intento si el objeto que
tiene delante ya está en `PROCESANDO` — pero ese guard solo protege el objeto que YA se leyó. Si
dos requests llaman a `solicitarValidacion` casi al mismo tiempo, las dos ejecutan `porId` antes
de que cualquiera haga commit, las dos ven `PENDIENTE`, las dos pasan el guard, las dos llaman
`saveGrabacionPort.guardar` y las dos llegan a `despacharDespuesDelCommit` → dos despachos
`@Async` → dos llamadas a `ValidacionIAPort.validar` por la misma grabación. Con Gemini real esto
es pagar la IA dos veces por una sola acción del aprendiz (mismo patrón que C-2 en `rocks`, ya
corregido ahí con `findByIdParaEscritura`).

`GrabacionV90PersistenceAdapter.java:25-28` (el `porId` sin lock) y
`GrabacionV90PersistenceAdapter.java` en general no tenían ninguna variante con bloqueo — no
existía el equivalente de `LoadRegistroHabitoPort.byIdParaEscritura` que sí tiene `habits`.

### 2. `PROCESANDO` para siempre ante un fallo

Con C-1 ya corregido (commit `0bd4a05`), `ProcesarValidacionV90Service.procesar()` ya no
envuelve la llamada a la IA en una transacción, y `validarSinDejarAtrapada` ya captura el caso
"la IA lanza" (timeout, error de red) y lo convierte en `NO_DISPONIBLE`. Pero eso cubre solo UNA
fuente de fallo. Antes de este cambio, el cuerpo de `procesar()` (línea ~56-70 de la versión
post-C-1) era:

```java
ResultadoValidacionV90 resultado = validarSinDejarAtrapada(usuarioId, grabacionId, grabacion);
switch (resultado.estado()) {
    case APROBADA -> grabacion.registrarAprobacion(resultado.feedbackJson(), clock);
    case RECHAZADA -> grabacion.registrarRechazo(resultado.feedbackJson(), clock);
    case NO_DISPONIBLE -> grabacion.registrarSinResultado(clock);
}
saveGrabacionPort.guardar(grabacion);   // <- si ESTO falla (Postgres caída, timeout de red
                                         //    hacia la base, constraint inesperado), la
                                         //    excepción sube sin capturar
```

Esa excepción llega a `DespacharValidacionV90Adapter.despachar()` (`@Async`), cuyo único manejo
es `catch (RuntimeException e) { log.error(...); }` — se loguea y se pierde. La grabación quedó
comprometida en Postgres como `PROCESANDO` (por el `solicitarValidacion` anterior) y **nunca
nadie vuelve a intentar sacarla de ahí**: ni un reintento del cliente (el dominio rechaza un
segundo intento mientras siga en `PROCESANDO`, ver `GrabacionV90.java:115-117`), ni un barrido
de fondo (no existe ninguno para V90). El aprendiz queda bloqueado en el onboarding sin
recurso, tal cual describe el escenario del informe.

## Qué cambié y por qué esa forma y no otra

### Fix 1 — Bloqueo pesimista + respuesta idempotente para el perdedor de la carrera

- **`LoadGrabacionV90Port`**: agregué `Optional<GrabacionV90> porIdParaEscritura(long id)`.
- **`SpringDataGrabacionV90Repository`**: agregué `findByIdParaEscritura` con
  `@Lock(LockModeType.PESSIMISTIC_WRITE)` sobre `SELECT g FROM GrabacionV90JpaEntity g WHERE
  g.id = :id`.
- **`GrabacionV90PersistenceAdapter`**: implementa el nuevo método delegando al repositorio.
- **`GrabacionV90Service`**: agregué `requireGrabacionPropiaParaEscritura` (mismo chequeo de
  propiedad que `requireGrabacionPropia`, pero usando la lectura con lock), y cambié
  `solicitarValidacion` para usarla, con un chequeo explícito:

  ```java
  GrabacionV90 grabacion = requireGrabacionPropiaParaEscritura(command.usuarioId(), command.grabacionId());
  if (grabacion.estadoIa() == EstadoIAv90.PROCESANDO) {
      return;
  }
  grabacion.procesarIntentoDeValidacion(clock);
  ...
  ```

**Por qué esta forma:**

- **Copié el patrón ya existente y ya probado en el repo** (`LoadRegistroHabitoPort
  .byIdParaEscritura` / `SpringDataRegistroHabitoRepository.findByIdParaEscritura` en `habits`,
  cerrado como C-2) en vez de inventar un mecanismo nuevo (`@Version` optimista, advisory lock de
  Postgres, etc.) — el propio informe de auditoría lo pide explícitamente ("Copiar el patrón
  `byIdParaEscritura` que `habits` ya tiene. Es el mismo bug tres veces", línea 191 del HTML).
  Bloqueo pesimista es correcto acá porque la ventana de contención es corta (una transacción que
  hace una lectura y un `UPDATE`, no la llamada a la IA — esa sigue pasando fuera de cualquier
  transacción, ver bloque `## Coherencia con C-1`).
- **Por qué el perdedor no relanza el guard del dominio en vez de un `if` explícito en el
  service:** `GrabacionV90.procesarIntentoDeValidacion()` ya rechaza reentrada a `PROCESANDO`,
  pero lanza `IllegalStateException`, que el `GlobalExceptionHandler` traduce a **409** (ver
  `shared/web/GlobalExceptionHandler.java:123-126`). En `habits` (C-2) el 409 para el perdedor es
  el comportamiento correcto (dos personas no pueden completar la misma roca dos veces; el
  segundo intento es un error real). Acá el enunciado de la tarea pide lo opuesto a propósito:
  el perdedor es un doble-clic o un reintento por timeout del **mismo** aprendiz sobre la
  **misma** solicitud en curso, así que el contrato debe ser idempotente (mismo 202 que si su
  request hubiera sido la única) — dejar que el dominio tire la excepción habría cambiado el
  código de respuesta que el cliente móvil ya espera. Por eso el chequeo de estado vive ANTES de
  llamar al dominio, en el service, y no se toca el guard de `GrabacionV90` (que sigue
  protegiendo, correctamente, contra el resto de las reentradas: dos llamadas a
  `registrarAprobacion`/`registrarRechazo`/`registrarSinResultado` sobre el mismo intento, por
  ejemplo).
- **Por qué NO se creó un lock separado solo para el chequeo de estado:** con el lock ya tomado
  en `requireGrabacionPropiaParaEscritura`, leer `grabacion.estadoIa()` inmediatamente después es
  gratis (mismo objeto, misma transacción) — no hace falta una segunda consulta.
- **Por qué `consultarEstado` (el GET de polling) NO usa la versión con lock:** el polling ocurre
  muchísimo más seguido que la escritura (el cliente consulta cada pocos segundos mientras
  espera el veredicto); bloquear la fila en cada GET generaría contención real contra el POST
  sin ningún beneficio, porque una lectura pura no necesita serializarse contra nada.

### Fix 2 — Rescate de `PROCESANDO` cuando aplicar o guardar el veredicto falla

- **`ProcesarValidacionV90Service.procesar()`**: extraje el `switch` + `saveGrabacionPort.guardar`
  a un método privado `aplicarResultadoYGuardar`, y lo envolví en un `try/catch` que, ante
  cualquier `RuntimeException`, loguea y llama a `rescatarDeProcesandoEterno(grabacionId)`.
- **`rescatarDeProcesandoEterno`**: **relee** la grabación desde `loadGrabacionPort.porId`
  (no reutiliza el objeto en memoria, que ya mutó), y **solo si Postgres todavía la ve en
  `PROCESANDO`** llama a `registrarSinResultado` y guarda de nuevo. Tiene su propio
  `try/catch` interno para no propagar un segundo fallo.

**Por qué esta forma y no otra:**

- **No inventé un estado nuevo.** El enunciado lo pide explícito y además ya estaba resuelto:
  `GrabacionV90.registrarSinResultado()` ya decide entre `PENDIENTE` (reintentable, si quedan
  intentos) y `REVISION_MANUAL` (si ya se gastaron los 3) — exactamente la misma máquina de
  estados que ya usa el camino "IA no disponible". Tratar "no se pudo guardar el veredicto" igual
  que "no se pudo obtener veredicto de la IA" es consistente con cómo el dominio ya modela la
  incertidumbre.
- **Por qué releer en vez de reusar el objeto en memoria:** si `aplicarResultadoYGuardar` falló
  DESPUÉS de que `grabacion.registrarAprobacion(...)` ya mutó el objeto pero ANTES de que
  `saveGrabacionPort.guardar` confirmara el `UPDATE`, el objeto en memoria dice `APROBADA` pero
  Postgres puede seguir diciendo `PROCESANDO` (si el fallo fue de red/conexión) — o, más raro,
  puede que el `UPDATE` sí haya llegado y lo que falló fue algo posterior (ninguna operación
  después de `saveAndFlush` en este método, pero es la razón de diseño: no asumir). Releer y
  chequear el estado real evita pisar un veredicto que en verdad sí se guardó, y evita también
  pisar un veredicto que otro camino haya escrito mientras tanto.
- **Por qué NO usar `REQUIRES_NEW`** (que es lo que sugiere literalmente el texto de corrección
  del informe, "registrar el fallo en `REQUIRES_NEW` desde el catch"): esa sugerencia asume la
  forma **anterior a C-1**, donde `procesar()` completo vivía dentro de un único
  `@Transactional` — ahí sí hacía falta forzar una transacción nueva para escapar de la que
  estaba a punto de revertirse. Después de C-1, `procesar()` ya NO tiene transacción ambiente
  (la lectura y la escritura son cada una su propia transacción corta de Spring Data JPA, ver el
  javadoc ya existente en la clase). Agregar `@Transactional` — con cualquier propagación — a
  `rescatarDeProcesandoEterno` sería volver a envolver el rescate en una transacción declarada a
  mano sin necesidad, y además chocaría con el problema de auto-invocación que la propia clase
  ya documenta para el caso de `@Async` (E-34): `rescatarDeProcesandoEterno` es un método privado
  de la misma clase, así que una anotación `@Transactional` en él NO pasaría por el proxy de
  Spring y no tendría ningún efecto real. Por eso se apoya, igual que el resto de la clase desde
  C-1, en la transacción corta e implícita que ya da cada llamada a
  `saveGrabacionPort.guardar`/`loadGrabacionPort.porId` vía Spring Data JPA — sin declarar nada
  nuevo.
- **Por qué el rescate tiene su propio try/catch en vez de dejar que la excepción suba:** si
  Postgres está genuinamente caída, el segundo intento de guardar también va a fallar. Se logea
  y se deja así — es el límite real de lo que se puede hacer sin un barrido de fondo (ver
  `## Requiere cambios que no hice` más abajo por qué no se construyó ese barrido).
- **Qué NO se tocó:** `validarSinDejarAtrapada` (el catch de C-1 para "la IA lanza") queda
  intacto — el nuevo `try/catch` de `aplicarResultadoYGuardar` es una capa adicional, no un
  reemplazo.

## Pruebas agregadas o modificadas — qué demuestra cada una

### `GrabacionV90ServiceTest.java` (unitario, mocks)

- **Modificada** `solicitarValidacionDeOtroUsuario`: antes stubeaba `loadGrabacionPort.porId`;
  ahora stubea `loadGrabacionPort.porIdParaEscritura`, porque `solicitarValidacion` ya no llama

- **Nueva** `solicitarValidacionEnPendienteDespachaUnaSolaVez`: camino feliz sin concurrencia —
  demuestra que el fix no rompió el flujo normal (`PENDIENTE` → transiciona, guarda, despacha

- **Nueva** `solicitarValidacionYaProcesandoEsIdempotente`: siembra una grabación ya en
  `PROCESANDO` y llama a `solicitarValidacion` — demuestra que el service **no** vuelve a llamar
  al dominio, **no** guarda de nuevo y **no** despacha una segunda vez; el método retorna sin
  excepción (contrato idempotente). Es la mitad "lógica de negocio" del fix del doble arranque;
  no puede demostrar el bloqueo de base en sí (eso es lo que hace la IT de abajo).

### `ProcesarValidacionV90ServiceTest.java` (unitario, mocks)

- **Nueva** `procesarRescataSiFallaElGuardadoDelVeredicto`: simula que el primer
  `saveGrabacionPort.guardar` lanza, y que una relectura posterior devuelve un objeto DISTINTO

  relee, ve `PROCESANDO` y fuerza `registrarSinResultado` + un segundo `guardar` exitoso. Verifica

- **Nueva** `procesarNoPropagaSiElRescateTambienFalla`: ambos `guardar` (el original y el del
  rescate) lanzan — demuestra que `procesar()` no deja escapar la excepción (se loguea y se

  contención.
- Las 4 pruebas preexistentes de este archivo (`procesarConAprobacion`, `procesarSinResultado`,
  `procesarIgnoraSiNoCoincideElUsuario`, `procesarSiLaIaLanzaNoDejaElRegistroAtrapado`) **no se
  modificaron**. Por lectura de código deberían seguir pasando igual: en todas ellas
  `saveGrabacionPort.guardar` no lanza, así que el nuevo `try/catch` de `aplicarResultadoYGuardar`
  nunca se activa y el camino ejecutado es idéntico al de antes del cambio.

### `GrabacionV90ValidacionConcurrenciaIT.java` (nueva, Testcontainers/Postgres real)

Sigue el patrón de `RocaDiariaConcurrenciaTest` (C-2) y de
`ProcesarValidacionV90ServiceTransaccionIT` (C-1): sin `@Transactional` de clase, seed vía
`JdbcTemplate` (auto-commit), `ExecutorService` con 6 hilos concurrentes.

- **`dobleSolicitudConcurrenteNoLlamaDosVecesALaIa`**: siembra una grabación `PENDIENTE`, lanza 6
  `solicitarValidacion` concurrentes sobre la MISMA grabación, y usa un `CountDownLatch` para
  retener la respuesta del mock de `ValidacionIAPort` hasta que las 6 solicitudes síncronas ya
  terminaron (esto aísla la carrera de "doble arranque" del ciclo normal de reintento — sin el
  latch, el primer intento podría resolverse y volver a `PENDIENTE` mientras los hilos perdedores
  todavía están en cola para el lock, abriendo una segunda ventana de carrera distinta a la que
  el test quiere medir). Debería demostrar: (1) ninguna de las 6 llamadas a
  `solicitarValidacion` lanza excepción; (2) `validacionIAPort.validar` se invoca **exactamente
  una vez**; (3) `intentos_ia` queda en `1`, no en 6; (4) el estado final es `PENDIENTE` (no
  `REVISION_MANUAL`, porque solo se consumió 1 de 3 intentos). Esta es la única prueba de las
  agregadas que puede demostrar de verdad el bloqueo de fila contra Postgres — un mock no
  alcanza, tal como pide el encargo.

## Coherencia con C-1

Releí `ProcesarValidacionV90Service.java` completo después de mi cambio (no solo el diff) para
confirmar esto:

- **La llamada a la IA sigue fuera de cualquier transacción.** `procesar()` no tiene
  `@Transactional` (ni lo tenía antes de mi cambio, ni se lo agregué). `validarSinDejarAtrapada`
  — el método que llama a `validacionIAPort.validar` — no lo toqué en absoluto: mismo cuerpo,
  misma firma, se sigue invocando en el mismo punto (línea `resultado =
  validarSinDejarAtrapada(...)`, ANTES de entrar al nuevo `try`). Todo lo que agregué
  (`aplicarResultadoYGuardar`, `rescatarDeProcesandoEterno`) vive DESPUÉS de esa llamada, nunca
  alrededor ni antes.
- **Ningún método nuevo tiene `@Transactional`.** Verificado leyendo el archivo completo: la
  única transacción explícita en todo el módulo `onboarding` para este flujo sigue siendo la de
  `GrabacionV90Service.solicitarValidacion` (que ya la tenía antes de C-3 y no hace ninguna
  llamada a IA — solo lee-con-lock, transiciona en memoria y guarda). `procesar()` y sus
  métodos privados nuevos dependen exclusivamente de las transacciones cortas e implícitas de
  Spring Data JPA, igual que dejó C-1.
- **`ProcesarValidacionV90ServiceTest` y `ProcesarValidacionV90ServiceTransaccionIT` siguen
  teniendo sentido** con la nueva lógica (razonamiento por lectura de código, no por corrida):
  - Las 4 pruebas viejas de `ProcesarValidacionV90ServiceTest` no fueron tocadas y ejercitan
    caminos donde `saveGrabacionPort.guardar` nunca lanza — el nuevo `try/catch` es transparente
    para ellas (ver sección de pruebas arriba).
  - `ProcesarValidacionV90ServiceTransaccionIT` (que NO modifiqué) verifica exactamente la
    propiedad que C-1 estableció: que durante `validacionIAPort.validar` no hay transacción
    activa (`laLlamadaALaIaOcurreFueraDeLaTransaccion`), que el veredicto se persiste
    (`persisteElVeredictoDeLaIa`) y que un fallo de la IA no deja el registro atrapado
    (`unFalloDeLaIaNoDejaElRegistroAtrapado`). Mi cambio no altera el orden de llamadas que esas
    tres pruebas observan (`validarSinDejarAtrapada` sigue corriendo primero, sin transacción;
    `aplicarResultadoYGuardar` sigue siendo el switch + guardar de siempre en el camino sin
    fallo). No debería haber motivo para que se rompan, pero **no las ejecuté** — queda para la
    corrida del coordinador confirmarlo con la salida real.
- **No modifiqué ningún archivo del hallazgo C-1** (`OnboardingAsyncConfig.java` no aparece en mi
  diff — confirmado con `git status`, ver arriba). El único archivo compartido entre C-1 y C-3 es
  `ProcesarValidacionV90Service.java`, y ahí el cambio es estrictamente aditivo después del punto
  donde termina la responsabilidad de C-1.

## Impacto en el contrato HTTP

Releí `GrabacionV90Controller.java` completo (no lo modifiqué — no aparece en mi diff). El
método relevante:

```java
@PostMapping("/{id}/validation")
public ResponseEntity<ValidacionV90Response> solicitarValidacion(@ActorAutenticado UserId actor,
                                                                   @PathVariable("id") Long id) {
    validarUseCase.solicitarValidacion(new SolicitarValidacionV90Command(actor, id));
    return ResponseEntity.accepted().body(ValidacionV90Response.accepted());
}
```

**El contrato no cambia: sigue siendo `202 {status:"processing"}` para `POST .../validation`, y
`GET .../validation` sigue siendo el polling, sin tocar `GrabacionV90Controller` ni
`ValidacionV90Response`.**

**Qué recibe el segundo llamador simultáneo (el que pierde la carrera), antes y después:**

- **Antes de este fix:** dependía de qué tan rápido corriera el `@Async` del primero.
  - Caso típico (la carrera real que describe C-3): el segundo también leía `PENDIENTE` sin
    lock, pasaba el guard y devolvía **202** — pero disparaba una SEGUNDA llamada a la IA (el
    bug).
  - Caso raro (si el segundo llegaba a leer después de que el primero ya hubiera comprometido
    `PROCESANDO`): el dominio rechazaba con `IllegalStateException` → el `GlobalExceptionHandler`
    lo traducía a **409 CONFLICT**.
- **Después de este fix:** el segundo llamador (el que, gracias al lock, lee después de que el
  primero comprometió) recibe exactamente **el mismo 202 `{status:"processing"}`** que el
  primero — porque `solicitarValidacion` ahora hace `return` sin excepción antes de llamar al
  dominio, y el controller ejecuta las mismas dos líneas de siempre. **No hay ningún caso, con
  este fix, en el que un doble-clic o un reintento del mismo aprendiz sobre la misma grabación
  reciba un código de respuesta distinto de 202** (mientras la grabación siga en `PROCESANDO`).
  El 409 sigue existiendo, pero ahora solo para un error real: pedir validar una grabación que
  ya tiene veredicto final (`APROBADA`/`RECHAZADA`) o que ya agotó sus 3 intentos — casos donde
  el dominio sigue lanzando `IllegalStateException` sin que yo lo haya tocado.

## Para la bitácora

```markdown
### E-XX: doble POST /validation sobre la misma grabación V90 disparaba dos llamadas a la IA; un fallo al guardar el veredicto dejaba la grabación en PROCESANDO sin salida

**Síntoma exacto:** dos requests concurrentes a `POST /api/v1/onboarding/v90-recordings/{id}/validation`
sobre la MISMA grabación devolvían ambas `202 {"status":"processing"}`, pero disparaban DOS
llamadas independientes a `ValidacionIAPort.validar` para el mismo `grabacionId` (doble costo de
IA). Por separado: si `saveGrabacionPort.guardar` fallaba durante `ProcesarValidacionV90Service
.procesar()` (ej. corte de conexión a Postgres), la grabación quedaba en `estado_ia = 'PROCESANDO'`
para siempre — ningún reintento del cliente la sacaba de ahí (`GrabacionV90.procesarIntentoDeValidacion`
rechaza reentrada mientras siga `PROCESANDO`) y no existía ningún barrido de fondo para V90.

**Causa real:** `GrabacionV90Service.solicitarValidacion` leía la grabación con
`loadGrabacionPort.porId` (sin bloqueo) antes de transicionarla a `PROCESANDO`. El guard de
`GrabacionV90.procesarIntentoDeValidacion()` (agregado para E-37) solo protege el objeto ya
leído en memoria — no evita que dos transacciones lean, cada una, la misma fila en estado
`PENDIENTE` antes de que cualquiera escriba. Por el segundo síntoma: `ProcesarValidacionV90Service
.procesar()` (después de la corrección de C-1) no tenía ningún manejo de fallo para el `saveGrabacionPort
.guardar` final — solo el `catch` genérico de `DespacharValidacionV90Adapter` (que solo loguea)
quedaba entre el fallo y una grabación atrapada.

**Solución:** (1) Nuevo método `LoadGrabacionV90Port.porIdParaEscritura`, con
`@Lock(PESSIMISTIC_WRITE)` en el repositorio (mismo patrón que
`LoadRegistroHabitoPort.byIdParaEscritura` en `habits`, C-2). `solicitarValidacion` lo usa y,
si al leer con el lock ya tomado la grabación está `PROCESANDO`, retorna sin excepción (202
idempotente) en vez de volver a llamar al dominio. (2) `ProcesarValidacionV90Service.procesar()`
envuelve el switch+guardar en un `try/catch` que, ante cualquier fallo, relee el estado real en
base y, si sigue en `PROCESANDO`, fuerza `registrarSinResultado()` (la misma máquina de estados
que ya usa "IA no disponible": vuelve a `PENDIENTE` si quedan intentos, o cae a `REVISION_MANUAL`).

**Cómo evitar que vuelva a pasar:** cualquier caso de uso que lea-transicione-guarde un agregado
mutable compartido entre requests concurrentes (un "arrancar algo" que cambia el estado a "en
curso") necesita SIEMPRE una de dos cosas: bloqueo pesimista en la lectura de escritura, o un
`UPDATE ... WHERE estado = 'X'` que devuelva filas afectadas — un guard en memoria dentro del
objeto de dominio (por más que ya exista, como acá con E-37) NUNCA alcanza por sí solo, porque no
existe hasta que alguien ya leyó la fila. Además: todo método que persiste el resultado de un
paso async de larga duración (una llamada a IA, un webhook, un job) necesita su propio manejo de
fallo en el guardado final, no solo en la llamada externa — un `catch` genérico río abajo (en el
adapter `@Async`) que solo loguea no es una red de recuperación, es un lugar donde el bug se
vuelve invisible.
```

## Para el registro de decisiones

```markdown
### D-XX: cómo sale una grabación V90 de PROCESANDO cuando el fallo ocurre DESPUÉS de tener veredicto de la IA (C-3)

**Contexto:** con C-1 ya resuelto, un fallo de la IA en sí misma ya cae correctamente a
"reintentar o revisión manual". Pero un fallo en el PASO SIGUIENTE — guardar el veredicto ya
obtenido — no tenía ningún manejo: la grabación podía quedar en `PROCESANDO` sin límite de
tiempo, sin ningún camino de salida.

**Decisión:** tratar el fallo de guardado exactamente igual que "IA no disponible": se relee el
estado real en base (nunca el objeto en memoria, que puede haber mutado sin llegar a
persistirse) y, si sigue `PROCESANDO`, se fuerza `registrarSinResultado()` — la misma máquina de
estados de siempre decide entre reintentar (`PENDIENTE`) o `REVISION_MANUAL`. Se descartó
explícitamente introducir un estado nuevo (ej. `ERROR_GUARDADO`) porque el aprendiz no necesita
distinguir "la IA no respondió" de "no se pudo guardar la respuesta de la IA" — en ambos casos
el siguiente paso correcto es el mismo (reintentar o pasar a revisión humana).

**Lo que queda explícitamente fuera de esta decisión (alcance):** un barrido de fondo
(`@Scheduled`) que detecte y rescate grabaciones que llevan más de N minutos en `PROCESANDO`
POR CUALQUIER MOTIVO (incluye el caso en que el propio proceso de la JVM muere entre el commit
de `solicitarValidacion` y la ejecución del `@Async`, que ningún cambio de este fix cubre). El
informe de auditoría lo sugiere como mejora ("barrido que devuelva a PENDIENTE lo que lleve más
de N minutos") y también sugiere, como alternativa de fondo, migrar V90 al modelo de cola
durable que ya usa `evidence`. Ninguna de las dos se implementó acá — ver
`## Requiere cambios que no hice`. Queda pendiente decidir cuál de las dos rutas se prioriza
cuando se aborde el resto de C-5 (schedulers sin lock distribuido), porque un barrido nuevo para
V90 tiene el mismo requisito de lock distribuido (ShedLock o `pg_try_advisory_xact_lock`) que ya
se señaló ahí para no duplicar trabajo entre instancias.
```

No topé con la necesidad de tocar ningún archivo prohibido (`pom.xml`,
`src/main/resources/application.yaml`, `src/test/resources/application.yaml`,
`docs/BITACORA_ERRORES.md`, `docs/MODULOS_A_AVANZAR.md`, `CLAUDE.MD`) para implementar el

Lo que SÍ quedó deliberadamente fuera de mi cambio, por ser una pieza de infraestructura más
grande que el alcance de este hallazgo (y que el propio encargo pidió no inventar):

- **Un `@Scheduled` que barra grabaciones huérfanas en `PROCESANDO`** (mencionado como mejora en
  el informe de auditoría, y relacionado con C-5 — "Once schedulers sin lock distribuido"). Si
  se decide construirlo, va a necesitar la misma solución de lock distribuido (ShedLock o
  `pg_try_advisory_xact_lock`) que C-5 ya pide para el resto de los schedulers del sistema — no
  tiene sentido resolverlo solo para V90 de forma aislada. Esto habría significado tocar
  `pom.xml` (para agregar la dependencia de ShedLock) si se hubiera implementado, que es
  justamente uno de los archivos que tengo prohibido tocar.
- **Migrar V90 al modelo de cola durable que ya tiene `evidence`** (la opción "Mejor:" del
  informe de auditoría) — es un cambio de arquitectura del flujo entero de validación IA de
  onboarding, no una corrección puntual de concurrencia, y excede el alcance de este ticket.

## Riesgos que le dejo a quien verifique

Ordenados por probabilidad de que algo falle:

1. **El más probable: no verifiqué que el proyecto compile con mis cambios.** Todos mis intentos
   de compilar/testear en esta sesión chocaron con el `target/` compartido (ver aviso al
   principio). Revisé el diff a mano dos veces buscando imports faltantes, tipos mal usados y
   nombres de método inventados, pero **no hay sustituto de un compilador real**. La prueba que
   lo detecta: cualquier corrida de `./mvnw test -Dtest=...` sobre estas clases — si hay un typo
   o un import que falta, va a fallar en la fase de compilación antes de llegar a ejecutar nada.
2. **La IT nueva (`GrabacionV90ValidacionConcurrenciaIT`) es la pieza más compleja y la que
   nunca corrí ni una vez.** El `CountDownLatch` que retiene la respuesta del mock de
   `ValidacionIAPort` hasta que las 6 solicitudes síncronas terminan es la parte más delicada:
   si el razonamiento sobre el orden de eventos (afterCommit síncrono → submit async → invokeAll
   retorna → se libera el latch) no es exactamente como lo describo en el diseño, el test podría
   quedar colgado (si el latch nunca se cuenta) o ser flaky (si en algún escenario de scheduling
   dos hilos SÍ alcanzan a llamar a `validar` antes de que se libere el latch, aunque por diseño
   solo uno debería). La prueba que lo detecta es la propia corrida de esa IT — si cuelga, el
   timeout de `pool.invokeAll(..., 30, TimeUnit.SECONDS)` o el `todasLasSolicitudesTerminaron
   .await(10, TimeUnit.SECONDS)` deberían hacerla fallar en vez de colgar indefinidamente, pero
   no until se corra no hay certeza.
3. **Riesgo de sintaxis/typo en la query JPQL nueva.** `@Query("SELECT g FROM
   GrabacionV90JpaEntity g WHERE g.id = :id")` con `@Lock(PESSIMISTIC_WRITE)` es una copia fiel
   del patrón de `habits`, pero nunca se ejecutó contra Hibernate. Si algo no calza (ej. el
   nombre de la entidad JPA), fallaría recién al arrancar el contexto de Spring en cualquiera de
   las pruebas `@SpringBootTest` (`GrabacionV90PersistenceAdapterTest`,
   `GrabacionV90ValidacionConcurrenciaIT`, `ProcesarValidacionV90ServiceTransaccionIT`), no en
   compilación.
4. **Riesgo menor: `rescatarDeProcesandoEterno` no está probado contra Postgres real**, solo con
   mocks (`ProcesarValidacionV90ServiceTest`). El comportamiento de releer-y-decidir depende de
   que `loadGrabacionPort.porId` en un segundo llamado realmente refleje el estado comprometido
   — con mocks eso se simula a mano (dos `thenReturn` distintos), pero no hay una IT que ejerza
   este camino contra la base real. Si se quiere cerrar ese hueco, haría falta una prueba que
   fuerce un fallo real de `saveGrabacionPort.guardar` contra Testcontainers (más difícil de
   lograr de forma determinística que con un mock) — la dejé fuera del alcance de esta sesión.
