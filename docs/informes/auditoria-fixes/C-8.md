# C-8 — informe de corrección

Fuente: `docs/informes/auditoria-seguridad-concurrencia-2026-09-01.html` — *"INCR y EXPIRE no
atómicos en los tres limitadores: una clave sin TTL bloquea para siempre"*, marcado "Media" en el
informe pero **subido a prioridad urgente** por el encargo: desde C-16/E-72 (ya aplicado), el
mismo defecto puede bloquear permanentemente el alta de cuentas nuevas de una IP, no solo el
reseteo de contraseña.

**Aviso de estado, leer primero — no corrí ninguna prueba.** El encargo pide explícitamente no
ejecutar builds (los intentos en paralelo de la ola anterior se pisaron entre sí y no terminaron
ninguno). Todo lo que sigue describe el código y las pruebas tal como quedaron escritas, leídas a
mano contra el resto del módulo — no una corrida en verde que yo haya presenciado. Quien verifique
debe correr:

```
./mvnw test -o -q -Dtest=LimitarSolicitudesResetRedisAdapterTest,ControlCuotaRedisAdapterTest,CodigoVerificacionEmailRedisAdapterTest -DfailIfNoTests=false
```

Los tres necesitan Docker (Testcontainers: Redis, vía `TestcontainersConfiguration`).

## Qué estaba mal

Los tres adaptadores hacían el mismo patrón defectuoso: `INCR` y `EXPIRE` como **dos comandos
Redis separados**, sin nada que los uniera atómicamente.

### 1. `LimitarSolicitudesResetRedisAdapter.java` (líneas 26-38, antes del cambio)

```java
Long intentos = redisTemplate.opsForValue().increment(claveRedis);   // 1) INCR
if (intentos == null) { return true; }
if (intentos == 1L) {
    redisTemplate.expire(claveRedis, ventana);                       // 2) EXPIRE, en OTRO comando
}
return intentos <= maximo;
```

Si el proceso muere (o Redis rechaza el segundo comando) entre el paso 1 y el 2, la clave queda
**sin TTL**. Como el `if` solo se ejecuta cuando `intentos == 1L`, ninguna llamada posterior vuelve
a intentar fijar el TTL — el contador sigue subiendo para siempre y, apenas supera `maximo`, esa
IP/email queda bloqueada sin fecha de vencimiento. Este puerto lo usan cuatro servicios de `users`
(`AccountRequestService`, `ConsultaEmailService`, `ResetContrasenaService`,
`VerificacionEmailService`) — desde C-16/E-72, también el alta de cuentas nuevas.

### 2. `ControlCuotaRedisAdapter.java` (líneas 39-57, antes del cambio)

Mismo patrón en `intentarConsumir` (`INCR` + `EXPIRE` separados, mismo defecto). Además, `liberar`
(línea 56) hacía:

```java
redisTemplate.opsForValue().decrement(claveDeHoy(actorId));   // DECR sin chequear si existe
```

`DECR` sobre una clave inexistente (porque ya expiró, o porque cruzó la medianoche) **crea una
clave nueva en `-1`, sin TTL**. Como la clave de ese día ya no la va a tocar nada más (la clave del
día siguiente usa una fecha distinta), esa clave `-1` queda huérfana en Redis para siempre — no
bloquea a nadie, pero es una fuga silenciosa.

### 3. `CodigoVerificacionEmailRedisAdapter.java`, método `registrarIntentoFallido` (líneas 59-70,
antes del cambio)

```java
Long intentos = redisTemplate.opsForValue().increment(claveIntentos);       // 1) INCR
if (intentos == null) { return; }
if (intentos == 1L) {
    Long ttlCodigoSegundos = redisTemplate.getExpire(claveCodigo);          // 2) leer TTL de OTRA clave
    if (ttlCodigoSegundos != null && ttlCodigoSegundos > 0) {
        redisTemplate.expire(claveIntentos, Duration.ofSeconds(ttlCodigoSegundos));  // 3) EXPIRE
    }
}
```

Acá son **tres** comandos separados (peor que los otros dos), y el tercero depende de leer el TTL
de una clave distinta (`codigo`) para copiarlo a `intentos`. Si el proceso muere entre el 1 y el 3,
`intentos` queda sin TTL. El impacto real es menor que en los otros dos: la propia clase ya
limpiaba `intentos` explícitamente cada vez que se pedía un código nuevo (`generarCodigo` hace
`redisTemplate.delete(claveIntentos(email))` antes de fijar el código), así que una clave
envenenada se autolimpia en cuanto ese email vuelve a pedir un código — pero si nunca lo pide, la
clave queda huérfana indefinidamente, y mientras tanto no hay nada que le devuelva un TTL si
alguien la reactivara por otra vía.

El comentario de la clase decía explícitamente que **evitaba a propósito** un script Lua ("el
riesgo es, como mucho, dejar pasar un intento de más — no filtrar el código"). Ese análisis
subestimaba el riesgo real: el problema no es "dejar pasar un intento de más", es la clave sin TTL
que C-8 señala. Ya no aplica; lo dejo corregido en el javadoc nuevo del archivo.

## Qué cambié y por qué

**Decisión: script Lua (`DefaultRedisScript` + `RedisTemplate.execute`), no `SET NX EX` + `INCR`.**
El propio informe ofrece las dos alternativas. Elegí Lua porque:

1. **Es realmente atómico de punta a punta.** Redis ejecuta un script Lua sin permitir que otro
   comando se intercale — no hay ninguna ventana observable entre el incremento y el TTL, ni
   siquiera del tamaño de un round-trip de red.
2. **Permite auto-reparación, y `SET NX EX` no.** El script no solo pregunta "¿es la primera vez
   que la clave llega a 1?" (que es lo que hacía el código viejo, y es frágil: una clave que ya
   estaba envenenada por el código viejo nunca vuelve a pasar por `== 1`), sino que pregunta
   **"¿esta clave tiene TTL ahora mismo?"** (`TTL == -1`). Con `SET NX EX`, si la clave ya existe
   (aunque esté envenenada sin TTL), el `NX` hace que el `SET` no haga nada — nunca se le fijaría un
   TTL a una clave ya envenenada. Con el chequeo de `TTL` dentro del script, la **siguiente llamada
   que toque una clave envenenada la repara sola**, sin intervención manual.
3. **No revisé el repo en busca de "cómo ya se resuelve esto en otro lado" y encontré un patrón
   Lua previo** (busqué `RedisScript`/`DefaultRedisScript`/`.lua` en todo `src/`, cero resultados):
   no hay convención existente que seguir ni que romper. El script queda declarado como
   `private static final RedisScript<Long>` en cada adaptador — no creé una clase ni un archivo
   compartido porque el encargo restringe el alcance a estos tres archivos y sus pruebas.

**No renueva el TTL en llamadas normales.** El chequeo es `TTL == -1`, no `intentos == 1`. Para una
clave sana (con TTL puesto), cada llamada nueva solo hace `INCR` — el `if` de Lua no dispara y el
TTL sigue corriendo igual que antes de este cambio. Esto es explícito porque el encargo lo pedía:
si cada llamada renovara el TTL, "60 por hora" pasaría a ser "60 seguidos sin pausa", una regla de
negocio distinta que nadie pidió.

**Milisegundos, no segundos.** Cambié `EXPIRE`/`Duration` por `PEXPIRE` con `ventana.toMillis()`
como `ARGV[1]`. El código viejo llamaba a `redisTemplate.expire(clave, Duration)`, que Spring Data
Redis resuelve a la precisión que haga falta; para no perder precisión al pasar la duración como
string a un script Lua, uso milisegundos siempre.

### Archivo por archivo

**`LimitarSolicitudesResetRedisAdapter.java`** — reemplacé el `increment` + `if` por un único
`redisTemplate.execute(INCREMENTAR_CON_TTL_SI_FALTA, List.of(claveRedis), String.valueOf(ventana.toMillis()))`.
Sin cambios de firma ni de comportamiento observable para el llamador (mismos cuatro consumidores
de `users` siguen funcionando igual en el camino sano).

**`ControlCuotaRedisAdapter.java`** — mismo script para `intentarConsumir`. Para `liberar`, agregué
un segundo script (`DECREMENTAR_SI_EXISTE`) que hace `EXISTS` + `DECR` condicional dentro del mismo
Lua: si la clave no existe, no hace nada (no la crea). Elegí resolverlo también con Lua, aunque el
informe solo sugería "DECR solo si la clave existe" (que en Java sería un `EXISTS` + `DECR` en dos
comandos): un `EXISTS`+`DECR` en dos pasos desde Java tiene la misma clase de problema que todo
C-8 señala (una ventana entre el chequeo y la acción, aunque acá el peor caso es solo crear una
clave huérfana, no bloquear a nadie) — como ya estaba escribiendo scripts Lua para el resto del
archivo, no tenía sentido dejar este caso con el mismo patrón que se está corrigiendo en el resto
del archivo.

**`CodigoVerificacionEmailRedisAdapter.java`** — until ahora el método `registrarIntentoFallido`
hacía `INCR` de `intentos` y, en un comando aparte, leía el TTL de `codigo` y lo copiaba a
`intentos`. El nuevo script hace las tres cosas en una sola llamada: `INCR` de `intentos`
(`KEYS[2]`), y si `intentos` no tiene TTL, lee el TTL de `codigo` (`KEYS[1]`) y se lo copia — todo
dentro del mismo script, así que no puede quedar un estado intermedio donde `intentos` ya subió
pero no tiene TTL. Actualicé el javadoc de la clase para sacar la explicación vieja de "por qué NO
usamos Lua acá", que quedó contradicha por este cambio.

**Lo que NO cambié:** la lógica de negocio de ninguno de los tres puertos (firmas, cuándo se
invalida un código, cuándo se libera cuota, qué excepción ven los llamadores). El fix es puramente
de atomicidad en el adaptador de infraestructura.

## Para la bitácora

```
### E-XX: INCR y EXPIRE en comandos Redis separados dejaban claves sin TTL — bloqueo
### permanente en los tres limitadores de tasa (C-8)

**Síntoma:** en teoría (nadie lo reportó todavía en producción), si el proceso moría justo entre
un INCR y su EXPIRE siguiente en cualquiera de los tres adaptadores Redis de limitación
(`LimitarSolicitudesResetRedisAdapter`, `ControlCuotaRedisAdapter`,
`CodigoVerificacionEmailRedisAdapter`), la clave del contador quedaba sin vencimiento. A partir de
ahí, esa IP/email/actor quedaba bloqueado para siempre (o, en `ControlCuotaRedisAdapter.liberar`,
un DECR sobre una clave ya vencida creaba una clave nueva en -1 sin TTL, huérfana pero inofensiva).
Desde C-16/E-72, el mismo defecto en `LimitarSolicitudesResetRedisAdapter` puede bloquear
permanentemente el ALTA de cuentas nuevas de una IP, no solo el reseteo de contraseña.

**Causa real:** los tres adaptadores hacían `INCR` (o `INCR` + lectura de otro TTL, en el caso del
código de verificación) y DESPUÉS `EXPIRE`/`PEXPIRE` como comandos Redis separados, sin nada que
los uniera atómicamente. El chequeo de "¿es la primera vez?" (`intentos == 1`) además no
autorreparaba una clave ya envenenada: solo intenta fijar TTL una vez en la vida de la clave.

**Solución:** los tres adaptadores ahora envuelven incremento + TTL en un único script Lua
(`DefaultRedisScript` + `RedisTemplate.execute`), que Redis ejecuta de punta a punta sin permitir
que otro comando se intercale. El chequeo pasó de "¿es la primera vez?" a "¿esta clave tiene TTL
AHORA MISMO?" (`TTL == -1`): eso hace que cualquier clave envenenada (por el código viejo, o por
cualquier causa futura) se autorepare en la SIGUIENTE llamada que la toque, sin limpieza manual.
`ControlCuotaRedisAdapter.liberar` además pasó a chequear `EXISTS` antes de `DECR`, dentro del
mismo script, para no crear una clave huérfana sobre una que ya venció.

**Cómo evitar que vuelva a pasar:** cualquier contador en Redis que combine "incrementar" +
"fijar TTL si hace falta" tiene que hacerlo en un único script Lua (`DefaultRedisScript`), nunca en
dos llamadas separadas al `RedisTemplate` — ni siquiera si la primera parece "atómica por sí sola"
(`INCR` lo es, pero la SECUENCIA de INCR-y-después-EXPIRE no). El chequeo de "hace falta fijar TTL"
debe ser sobre el ESTADO ACTUAL de la clave (`TTL == -1`), no sobre el valor que acaba de devolver
el incremento (`== 1`) — lo segundo no autorrepara nada si la clave ya estaba mal por otro motivo.
```

## Para el registro de decisiones

```
### D-XX: los contadores de límite de tasa en Redis usan script Lua para incrementar + fijar
### TTL, nunca dos comandos separados

Contexto: C-8 encontró que los tres limitadores de tasa en Redis (`LimitarSolicitudesResetPort`,
`ControlCuotaRenasiaPort`, `CodigoVerificacionEmailPort`) hacían `INCR` y `EXPIRE` como comandos
separados, dejando una ventana donde una clave podía quedar sin TTL para siempre si el proceso
moría (o Redis rechazaba el segundo comando) entre uno y otro.

Decisión: cualquier contador nuevo en Redis que necesite "incrementar y, si hace falta, fijar TTL"
usa un script Lua (`DefaultRedisScript<Long>` + `RedisTemplate.execute`), no dos llamadas
separadas al `RedisTemplate` ni la alternativa `SET NX EX` + `INCR` (esa alternativa no permite
autorreparar una clave que ya quedó sin TTL por una causa anterior, porque el `NX` no hace nada si
la clave ya existe). El chequeo de "¿hace falta fijar TTL?" se hace sobre el TTL actual de la
clave (`TTL == -1`), no sobre si el contador acaba de llegar a 1 — así cualquier clave envenenada
se autorepara en la siguiente llamada que la toque, sin necesidad de un script de limpieza manual
en producción.

Se evaluó explícitamente no usar Lua (el criterio de `CodigoVerificacionEmailRedisAdapter` antes de
este cambio: "el riesgo es, como mucho, dejar pasar un intento de más"). Se descarta ese criterio:
el riesgo real no era ese, era la clave sin TTL que C-8 describe, y con cuatro consumidores del
mismo puerto (`AccountRequestService`, `ConsultaEmailService`, `ResetContrasenaService`,
`VerificacionEmailService`) más el alta de cuentas nuevas (C-16/E-72) dependiendo de
`LimitarSolicitudesResetRedisAdapter`, el costo de un bloqueo permanente ya no es aceptable a
cambio de evitar una dependencia de scripting que Redis soporta de forma nativa desde siempre.
```

## Claves ya envenenadas: qué puede existir hoy en Redis, y cómo limpiarlas

**No tengo acceso al Redis de ningún entorno para confirmar si existen hoy.** Lo que sigue es
análisis de qué es POSIBLE que exista, no una constatación.

- **Se autorreparan solas, sin intervención, en cuanto alguien vuelve a intentar.** El fix nuevo
  hace que la primera llamada siguiente sobre una clave envenenada (de cualquiera de los tres
  adaptadores) le fije el TTL que le faltaba. Como el limitador se consulta en CADA intento del
  usuario/IP afectado, cualquier IP/email que hoy esté bloqueada permanentemente por este defecto
  se autorrepara la próxima vez que esa misma persona vuelva a intentar la operación — no hace
  falta esperar a que alguien corra un script de limpieza para que esa persona deje de estar
  bloqueada.
- **Lo que NO se autorrepara solo:** una clave envenenada que pertenece a una IP/email que
  **nunca vuelve a intentar** (la persona se rindió, o cambió de IP). Esa clave queda en Redis para
  siempre — sin TTL, sin nadie que la vuelva a tocar. No bloquea a nadie (nadie más la consulta),
  pero es una fuga de memoria lenta en Redis. Con el volumen de tráfico actual del sistema (sin
  usuarios reales todavía, según el estado documentado del proyecto) es improbable que haya muchas,
  pero en un entorno con tráfico real conviene un barrido periódico.
- **Propuesta de limpieza (no ejecutada por mí, y no tengo cómo probarla contra un Redis real
  en este encargo):** un script que recorra las claves de los tres prefijos
  (`reset-password:rl:*`, `renasia:cuota:*`, `email-verification:intentos:*`) con `SCAN` (nunca
  `KEYS` en producción, por el bloqueo de un solo hilo que implica sobre un dataset grande), y para
  cada una consulte `TTL`: si es `-1`, decidir entre (a) borrarla directamente (son contadores, no
  hay dato de negocio que perder) o (b) fijarle un TTL corto (ej. 1 hora) para que se autolimpie
  sola sin un borrado inmediato. Prefiero (a): son puramente contadores efímeros, no hay ningún
  caso en el dominio donde perder una de estas claves sea observable para un usuario real (en el
  peor caso, alguien recupera un intento de más — el mismo riesgo que el comentario viejo de
  `CodigoVerificacionEmailRedisAdapter` ya aceptaba como tolerable). Ejemplo de script (Lua, para
  correr con `redis-cli --eval` o similar, NO ejecutado por mí):

  ```lua
  -- purgar_claves_sin_ttl.lua — recibe el patron como ARGV[1], p.ej. "reset-password:rl:*"
  local cursor = "0"
  local borradas = 0
  repeat
      local resultado = redis.call("SCAN", cursor, "MATCH", ARGV[1], "COUNT", 100)
      cursor = resultado[1]
      for _, clave in ipairs(resultado[2]) do
          if redis.call("TTL", clave) == -1 then
              redis.call("DEL", clave)
              borradas = borradas + 1
          end
      end
  until cursor == "0"
  return borradas
  ```

  Correr una vez por cada uno de los tres prefijos, en un entorno con Redis real, ANTES o DESPUES
  de desplegar este fix (da igual el orden: después del deploy, cualquier clave sin TTL que quede
  ya es una que nadie volvió a tocar, así que es segura de borrar sin esperar).

2. **No verifiqué que `redisTemplate.execute(RedisScript, List<K>, Object...)` serialice el
   `ARGV` de milisegundos exactamente como espero.** `StringRedisTemplate` usa
   `StringRedisSerializer` para claves y valores; asumo (por ser el comportamiento estándar
   documentado de Spring Data Redis) que el mismo serializer se usa para los argumentos del script
   cuando se pasa un `String`, así que `ARGV[1]` le llega a Lua como la representación en texto del
   número de milisegundos (p.ej. `"10000"`), que Redis interpreta correctamente en comandos como
   `PEXPIRE`. Si el `ScriptExecutor` por defecto serializara los argumentos de otra forma (por
   ejemplo, con el serializer de Java por defecto en vez del de String), `PEXPIRE` fallaría con un
   error de tipo — algo que ninguna prueba mockeada detectaría, solo Testcontainers contra Redis
   real, que es justo por lo que las pruebas nuevas están armadas así.
3. **Los tres tests de concurrencia (`elLimiteSeRespetaBajoConcurrencia` en cada archivo) son los
   más frágiles.** Dependen de que un pool de 10 hilos contra un Redis de Testcontainers se
   comporte de forma predecible bajo el timeout de 30s. Si el entorno de CI es lento, podrían
   fallar por timeout en vez de por una aserción real — la señal para distinguir un caso del otro
   es si `invokeAll` devuelve menos elementos de los esperados (timeout) antes de asumir que el
   límite está roto (mismo criterio que ya deja documentado
   `AccountRequestRateLimitConcurrenciaTest` para su propio test de concurrencia).
