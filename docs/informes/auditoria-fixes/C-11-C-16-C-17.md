## C-11 — SMTP dentro de `@Transactional` en la invitación de staff

### Qué estaba mal

`UserAccountService.java` (HEAD, antes del cambio), método `inviteStaff` (líneas 101-112) y su
colaborador `grantTemporaryPasswordAndNotify` (líneas 114-127):

```java
// líneas 101-112
@Transactional
public UserId inviteStaff(InviteStaffCommand command) {
    User actor = requireActiveUserGuard.of(command.actorId());
    UserId newId = UserId.of(idGenerator.newId());
    User invited = User.invite(newId, new Email(command.email()), command.fullName(), command.role(), actor);
    User saved = saveUserPort.save(invited);
    ensureMentorProfileIfNeeded(saved);
    grantTemporaryPasswordAndNotify(saved);           // <- manda el correo AQUÍ, dentro de la tx
    events.publishEvent(new UsuarioRegistradoEvent(saved.id(), clock.now()));
    return saved.id();
}

// líneas 123-127
private void grantTemporaryPasswordAndNotify(User user) {
    String temporaryPassword = generateTemporaryPassword();
    saveCredencialPort.guardar(user.id(), new Credencial(passwordEncoder.encode(temporaryPassword), clock.now()));
    enviarEmailPort.enviarInvitacionStaff(user.email().value(), temporaryPassword);   // <- SMTP
}
```

`enviarEmailPort.enviarInvitacionStaff(...)` (implementado por `SmtpEnviarEmailAdapter`) hace una
llamada de red bloqueante a un servidor SMTP. Con la anotación `@Transactional` en `inviteStaff`,
esa llamada corre con una conexión de Hikari ya tomada del pool. El informe midió hasta 15s
(3 reintentos de 5s) de un SMTP que no responde reteniendo esa conexión — con un pool chico (10
conexiones, según E-1 del mismo informe), un admin cargando una cohorte de staff puede agotarlo
para **toda** la API, no solo para las invitaciones. Es el mismo defecto de forma que C-1
(`ProcesarValidacionV90Service`, ya corregido en el commit `0bd4a05`): una llamada externa lenta
corriendo con una transacción de Postgres abierta.

### Qué cambié y por qué

Archivo: `src/main/java/com/renaser/os/users/application/services/UserAccountService.java`.

- El guardado de la credencial (`saveCredencialPort.guardar`, rápido, una escritura a Postgres)
  se queda DENTRO de la transacción — sigue siendo atómico con la creación del usuario, que es lo
  que se necesita: no debe poder existir un usuario invitado sin su credencial.
- El envío del correo se difiere con `TransactionSynchronizationManager.registerSynchronization(...)`
  + `afterCommit()` — **mismo patrón que `MensajeService.publicarDespuesDelCommit`** (chat, ya en
  el repo), que es exactamente lo que sugería la corrección del informe ("Enviar en `afterCommit`,
  como hace `MensajeService`"). Elegí este patrón y no partir el método en dos transacciones cortas
  (el patrón de C-1) porque acá, a diferencia de la validación IA, sí hace falta que el commit ya
  haya ocurrido antes de mandar el correo: si el commit fallara después de mandar el correo, el
  invitado recibiría una contraseña para una cuenta que no llegó a existir. `afterCommit` garantiza
  el orden correcto sin necesidad de dos métodos `@Transactional` separados.
- Si no hay una transacción Spring activa (tests que instancian el servicio con `new`, sin proxy),
  se manda directo — mismo fallback que ya tiene `MensajeService`.

**Decisión explícita sobre qué pasa si el correo falla** (pedida en el encargo): el fallo se
captura y se loguea en `ERROR` (`enviarInvitacionSinPerderElAlta`), **sin propagarse**. Elegí no
propagar porque para cuando el correo se intenta mandar, la invitación YA COMMITEÓ — no hay nada
que "deshacer", y dejar que la excepción se escape de un callback `afterCommit` no revertiría el
alta (ya es tarde), solo ensuciaría el log con una `TransactionSynchronization.afterCommit threw
exception` de Spring en vez de un mensaje claro. Tampoco agregué un reintento de ENVÍO ni un nuevo
endpoint de "reenviar invitación": no hace falta uno nuevo porque **el invitado ya tiene una
`Credencial` real guardada** (aunque no la conozca) — si el correo con la contraseña temporal
nunca llega, la persona puede recuperar acceso por el flujo YA EXISTENTE de "olvidé mi contraseña"
(`SolicitarResetContrasenaUseCase`, público, `POST /api/v1/auth/password/reset-request`), exactamente
el mismo camino que ya usa cualquier otro usuario. No queda varado, y no inventé infraestructura
nueva. Esto es una decisión de producto tomada por mí (no confirmada con el dueño del proyecto):
lo dejo explícito en el bloque de decisiones para que se pueda revisar.

Lo que el admin ve: nada distinto a hoy. `inviteStaff` sigue devolviendo el `UserId` normalmente;
un fallo de SMTP es invisible para el llamador HTTP (ya lo era antes de mi cambio: el catch de
`SmtpEnviarEmailAdapter.enviar` convierte cualquier error en `EnvioEmailFallidoException`, y antes
de mi cambio esa excepción SÍ se propagaba dentro de la transacción — lo que en los hechos revertía
TODO el alta, un comportamiento peor: ni el usuario ni la credencial quedaban creados, y el admin
recibía un 503 sin ninguna invitación real detrás. Con el cambio, la invitación queda firme y solo
se pierde el aviso por correo).

### Pruebas

1. **`UserAccountServiceTest.inviteStaffNoPierdeElAltaSiFallaElEnvioDelCorreo`** (unitaria, Mockito,
   ya existía la clase). Mockea `enviarEmailPort.enviarInvitacionStaff` para tirar
   `EnvioEmailFallidoException`, llama `inviteStaff`, y verifica que **no se propaga ninguna
   excepción**, que devuelve un `UserId`, y que `saveUserPort.save`/`saveCredencialPort.guardar` sí
   se invocaron. Como en este test no hay una transacción Spring real, ejercita la rama
   "sin sincronización activa" (envío directo) — prueba el manejo del fallo, no el orden
   temporal contra el commit (eso es lo que hace el test de integración de abajo).
2. **`UserAccountServiceInvitarStaffTransaccionIT`** (nueva, Testcontainers, mismo criterio que
   `ProcesarValidacionV90ServiceTransaccionIT` de C-1: autowirea el caso de uso por su interfaz
   pública para que el proxy `@Transactional` de Spring esté realmente en juego).
   - `elEnvioDeCorreoOcurreFueraDeLaTransaccion`: mockea `EnviarEmailPort` con `@MockitoBean`, y
     dentro del mock captura `TransactionSynchronizationManager.isActualTransactionActive()` en el

   - `unFalloDeEnvioNoPierdeLaInvitacion`: el mock tira `EnvioEmailFallidoException`; verifica por
     SQL directo (`SELECT hash_contrasena FROM renaser.usuarios WHERE id = ?`) que la credencial

**No verificado por mí:** no vi la salida de ninguna de las dos. La corrida se le pidió al

## C-16 — Rate limit por `COUNT` (check-then-act) y token de verificación consumido antes del INSERT

### Qué estaba mal

`AccountRequestService.java` (HEAD, antes del cambio):

```java
// líneas 118-133 (submit)
@Transactional
public AccountRequestId submit(SubmitAccountRequestCommand command) {
    rejectIfRateLimitExceeded(command.requestIp());
    requireEmailVerificado(command.email(), command.verificationToken());   // <- consume el token AQUÍ

    Email email = new Email(command.email());
    User usuario = User.registrarPendienteAprobacion(UserId.of(idGenerator.newId()), email, command.fullName());
    saveUserPort.save(usuario);                                            // <- puede fallar (UNIQUE) DESPUÉS
    ...
}

// líneas 237-245 (rejectIfRateLimitExceeded)
private void rejectIfRateLimitExceeded(String requestIp) {
    if (requestIp == null) return;
    long recent = loadAccountRequestPort.countSubmittedFromIpSince(requestIp,
            clock.now().minus(Duration.ofHours(1)));                       // <- 1) LEE cuántos van
    if (recent >= RATE_LIMIT_PER_HOUR) {
        throw new RateLimitExceededException(...);
    }
}                                                                            // <- 2) el INSERT que "cuenta" pasa DESPUÉS, en otra sentencia
```

Dos defectos distintos, ambos en el mismo método:

1. **Check-then-act del límite**: `countSubmittedFromIpSince` (un `SELECT COUNT`) y el `INSERT`
   real de la solicitud son dos sentencias separadas, sin nada que las una atómicamente. N envíos
   concurrentes desde la misma IP pueden leer el mismo `COUNT` (por debajo del límite) antes de que
   ninguno haga commit, y todos pasar — el límite de 60/hora se puede superar en ráfaga.
2. **Token de un solo uso, gastado antes de saber si el resto va a funcionar**:
   `requireEmailVerificado` llama a `tokenVerificacionEmailPort.consumir(verificationToken)`, que es
   un `GETDEL` atómico en Redis — se borra al leerse. Si el `INSERT` de más abajo falla (el caso
   más común: el correo ya tenía cuenta o solicitud, lo que hoy solo se descubre en el `UNIQUE` de
   Postgres), el token ya está perdido y la persona tiene que reverificar su correo de cero.

### Qué cambié y por qué

Archivo: `src/main/java/com/renaser/os/users/application/services/AccountRequestService.java`.

**Límite por IP → Redis atómico, no Postgres.** Reemplacé `countSubmittedFromIpSince` por
`LimitarSolicitudesResetPort.registrarIntento(clave, ventana, máximo)` — el mismo puerto que
`VerificacionEmailService` y `ConsultaEmailService` **ya usan hoy** para sus propios límites por
IP (`ConsultaEmailService` lo dice explícito en su javadoc: *"el limite vive aca dentro
reutilizando LimitarSolicitudesResetPort — que es lo que CLAUDE.MD §5.3.6 anticipaba"*). No inventé
un puerto nuevo: reutilicé uno que ya está probado y en producción para el mismo tipo de problema,
tal como pedía el encargo ("leé qué limitadores Redis ya existen antes de decidir"). Este puerto
hace el chequeo-y-registro en una sola llamada (`INCR` de Redis), así que no queda la ventana entre
"leer cuántos van" y "escribir uno más" que permitía la ráfaga. Sigue siendo real entre instancias
(CLAUDE.MD §5.3.6): Redis es compartido, no en memoria.

**Nota de dependencia (pedida en el encargo):** `LimitarSolicitudesResetRedisAdapter`, el adaptador
detrás de ese puerto, es uno de los tres adaptadores marcados por **C-8** ("INCR y EXPIRE no
atómicos... una clave sin TTL bloquea para siempre") — hallazgo de otro agente. **No toqué ese
adaptador**, lo uso tal como está. Si C-8 se corrige después, este código no necesita cambios (usa
el puerto, no el adaptador). Si C-8 NO se corrige, este rate limit hereda su mismo defecto residual
(el caso extremo: el proceso muere justo entre el primer `INCR` y su `EXPIRE`, dejando esa IP sin
límite hasta que alguien la libere a mano) — no es nuevo, ya lo tenían `VerificacionEmailService` y
`ConsultaEmailService`.

**Email ya registrado, chequeado ANTES de consumir el token.** Agregué
`rejectIfEmailYaRegistrado(email)`, que llama a `loadUserPort.byEmail(email)` y
`loadAccountRequestPort.existePorEmail(email)` (los dos puertos ya inyectados en la clase, no
agregué ninguno nuevo) **antes** de `requireEmailVerificado`. Si cualquiera de los dos dice que el
correo ya existe, tiro `IllegalStateException("Ya existe una cuenta o solicitud con este correo")`
sin haber tocado el token. Elegí `IllegalStateException` (no una excepción nueva) por dos motivos:
(a) es el mismo tipo que ya usa este archivo para "ya existe/ya se decidió" (ver
`AccountRequest.java:117`, `User.java:85`, `ParticipacionProgramaService.java:98`), y (b)
`GlobalExceptionHandler` ya la mapea a 409 — el MISMO código HTTP que el `DataIntegrityViolationException`
que se disparaba antes en este caso (ver `## Impacto en el frontend`), así que no hacía falta tocar
`GlobalExceptionHandler` (archivo que no es mío, aunque no está en la lista de prohibidos — preferí
no acercarme).

Esto **no elimina** la carrera de un `submit` exactamente simultáneo para el mismo correo (esa la
sigue resolviendo el `UNIQUE` de Postgres, como siempre) — lo dejé documentado en el javadoc del
método. Lo que sí cubre es el caso común y no concurrente: alguien reintenta con un correo que ya
tenía cuenta desde antes, sin gastar un token que iba a fallar de todos modos.

`loadAccountRequestPort.countSubmittedFromIpSince` quedó sin uso en este servicio. No borré el
método del puerto ni su adaptador ni su test (`AccountRequestPersistenceAdapterTest`): borrarlos
hubiera significado tocar `AccountRequestPersistenceAdapter.java` y su test, más superficie de la
necesaria para un hallazgo "baja". Lo dejo anotado como limpieza pendiente, no ejecutada.

### Pruebas

**Unitarias (Mockito), en `AccountRequestServiceTest.java`:**

1. `submitRechazaPorLimiteDeIpSinConsumirElToken`: mockea `registrarIntento` para devolver
   `false`, espera `RateLimitExceededException`, y verifica `tokenVerificacionEmailPort.consumir`
   **nunca** se llamó y no se guardó nada.
2. `submitRechazaUnCorreoConCuentaExistenteSinConsumirElToken`: `loadUserPort.byEmail` devuelve un

Además tuve que agregar el mock `LimitarSolicitudesResetPort` al `setUp()` de la clase (con

   de verdad demuestra "el INSERT fallido no consume el token" contra el adaptador Redis real, no
   solo contra un mock que registra si `consumir` se llamó.

## C-17 — Primer login social duplicado recibe 409 en vez de "solicitud en revisión"

### Qué estaba mal

`CompletarRegistroSocialService.java` (HEAD, antes del cambio), método `completar` (líneas 41-55):

```java
@Override
public AccountRequestId completar(CompletarRegistroSocialCommand command) {
    RegistroPendienteSocial registro = tokenRegistroPendienteSocialPort
            .consumir(command.registroPendienteToken())
            .orElseThrow(RegistroPendienteSocialInvalidoException::new);

    String verificationToken = tokenVerificacionEmailPort.generar(registro.email(), ...);

    return submitAccountRequestUseCase.submit(SubmitAccountRequestCommand.porProveedorSocial(registro.email(),
            command.fullName(), command.phone(), command.city(), verificationToken, command.requestIp(),
            registro.proveedor(), registro.sujetoProveedor()));
}
```

Desde D-65 (2026-09-01), el primer login social con una identidad nueva **no** abre la
`AccountRequest` en el momento: solo guarda un `RegistroPendienteSocial` en Redis y devuelve un
token de continuación (`AutenticacionSocialService.retenerIdentidadPendiente`). Cada vez que se
llama `POST /auth/social` para la misma identidad se genera un token INDEPENDIENTE — el servicio
no se acuerda de tokens anteriores. Si dos de esos tokens (dos pestañas, un reintento de red del
celular, un doble tap en "Confirmar") terminan llamando a `POST /auth/social/complete` casi al
mismo tiempo, ambos ejecutan `submitAccountRequestUseCase.submit(...)`: el primero crea el `User` y
la `AccountRequest` (dentro de su propia `@Transactional` en `AccountRequestService.submit`), el
segundo choca contra el índice `UNIQUE` de `usuarios.email` o `solicitudes_cuenta.email`
(`V1__baseline_renaser.sql:141` y `:165`) y su `DataIntegrityViolationException` se propaga sin que
nada la atrape acá — termina en el 409 genérico de
`GlobalExceptionHandler.handleIntegridad` ("La operacion entra en conflicto con datos que ya
existen") en vez del mismo "tu solicitud ya está en revisión" que la persona ya vería si tocara
"Continuar con Google" una TERCERA vez (`ResultadoLoginSocial.SolicitudEnRevision`, que sí funciona
bien porque en ese camino `AutenticacionSocialService.iniciarSesion` consulta
`loadAccountRequestPort.porOrigenSocial` ANTES de intentar nada).

### Qué cambié y por qué

Archivo: `src/main/java/com/renaser/os/users/application/services/CompletarRegistroSocialService.java`.

Envolví la llamada a `submitAccountRequestUseCase.submit(...)` en un `try/catch` de
`DataIntegrityViolationException`. En el catch, `solicitudYaCreadaPorOtraLlamada` reconstruye el
`OrigenSocial` (proveedor + sujeto, que ya tenía en `registro` — nunca por correo, mismo criterio
de seguridad de todo `docs/MODULO_AUTH.md §6.4`) y llama a
`loadAccountRequestPort.porOrigenSocial(origen)` (puerto que YA existía, ya lo usa
`AutenticacionSocialService` para el mismo propósito). Si encuentra una solicitud de esa MISMA
identidad y está `isPending()`, devuelvo su `id()` — exactamente lo que hubiera devuelto la llamada
que ganó la carrera. Si no la encuentra (el conflicto de `UNIQUE` vino de otro lado — por ejemplo,
alguien mandó un alta por formulario con el mismo correo casi al mismo tiempo, que NO es la misma
identidad social), relanzo la excepción original: prefiero el 409 genérico antes que inventarle a
alguien el id de una solicitud ajena.

Elegí catch-y-recuperar en vez de, por ejemplo, chequear `porOrigenSocial` ANTES de llamar a
`submit()` (equivalente al `rejectIfEmailYaRegistrado` de C-16) porque acá el objetivo es distinto:
en C-16 quiero RECHAZAR limpio sin gastar un token; acá quiero que la llamada que "pierde" la
carrera **tenga éxito igual**, devolviendo lo mismo que la que ganó — es explícitamente el mismo
criterio que ya aplica `vincularIdentidadSocial` en este módulo ("el doble tap del cliente móvil no
es un error"). Chequear antes no alcanzaría: dos llamadas exactamente simultáneas pasarían las dos
el chequeo previo igual (ninguna commiteó todavía) y solo una fallaría después en el INSERT — hace
falta el catch de todos modos para cubrir la carrera real, así que hacerlo antes hubiera sido
trabajo duplicado sin cerrar el caso que de verdad importa.

### Pruebas

En `CompletarRegistroSocialServiceTest.java` (existente, agregué al final):

1. `dosConfirmacionesConcurrentesDeLaMismaIdentidadDevuelvenLaSolicitudGanadora`: mockea
   `submitAccountRequestUseCase.submit` para tirar `DataIntegrityViolationException`, mockea
   `loadAccountRequestPort.porOrigenSocial(origen)` para devolver una `AccountRequest` pendiente de
   la MISMA identidad, y afirma que `completar()` devuelve el id de esa solicitud en vez de dejar
   escapar la excepción — esto demuestra exactamente "qué respuesta recibe el cliente": el mismo
   valor de retorno (`AccountRequestId`) que produce el camino feliz, que el controller (sin
   cambios) mapea al mismo 202 de siempre.
2. `unConflictoDeUniqueSinSolicitudDeLaMismaIdentidadRelanzaElErrorOriginal`: mismo disparo de
   `DataIntegrityViolationException`, pero `porOrigenSocial` devuelve vacío — afirma
   (`isSameAs(fallo)`) que se relanza la MISMA excepción original, no una nueva ni un `null`.

También tuve que agregar el mock `LoadAccountRequestPort` al constructor de prueba de esta clase
(nuevo parámetro del servicio).

## Impacto en el frontend

Revisé `AutenticacionController.java` (el único controller que expone estos casos de uso) y
`GlobalExceptionHandler.java` línea por línea — no por deducción — para esta sección.

- **`AutenticacionController.loginSocial` y `.completarRegistroSocial`: SIN CAMBIOS de código.**
  No toqué ese archivo. El `switch` sobre `ResultadoLoginSocial` sigue exactamente igual (200 /
  202 / 202 / 409, las cuatro variantes de siempre), y `completarRegistroSocial` sigue devolviendo
  siempre `202` + `AccountRequestIdResponse` cuando `completar()` no lanza. Mi cambio en
  `CompletarRegistroSocialService` NO agrega una variante nueva ni cambia la firma de retorno
  (sigue siendo `AccountRequestId`) — desde el punto de vista del controller y de la app, es
  indistinguible de un `submit()` exitoso normal.

  **Lo que SÍ cambia, observable solo en la ventana de carrera de C-17:** antes, el segundo de dos
  `POST /auth/social/complete` casi simultáneos para la misma identidad social recibía **409**
  (`ApiErrorResponse{message: "La operacion entra en conflicto con datos que ya existen"}`). Con el
  arreglo, ese mismo segundo request recibe **202** con
  `AccountRequestIdResponse{accountRequestId: <el mismo id que ya vio o va a ver el primero>}`. Es
  un cambio de status code, pero SOLO en esa ventana de carrera (dos confirmaciones casi
  simultáneas de la misma identidad), y es una mejora estricta: antes era un error genérico que no
  decía nada útil, ahora es el mismo éxito que ya maneja la app para el flujo normal de alta social.
  No hace falta que el frontend cambie nada para aprovecharlo (202 + `accountRequestId` ya es un
  caso que maneja), pero **si el frontend tenía algún manejo especial para el 409 de este endpoint
  en particular** (no lo vi documentado en `docs/MODULO_AUTH.md` ni en el controller), dejaría de
  dispararse en ese caso puntual. Avisar al equipo de RN por las dudas.

- **`AccountRequestService.submit` (usado por `POST /api/v1/account-requests` vía otro controller
  que no toqué, y por `POST /auth/social/complete`): el código de estado NO cambia para ningún
  caso ya existente.** Antes, un correo ya registrado terminaba (tarde o temprano, en el `UNIQUE`
  de Postgres) en `DataIntegrityViolationException` → **409** vía `handleIntegridad`. Ahora termina
  antes, en `IllegalStateException` → **409** vía `handleConflict` — **mismo status code, mismo
  shape de respuesta (`{message: string}`)**, la única diferencia es el TEXTO del mensaje:
  - Antes: `"La operacion entra en conflicto con datos que ya existen"`
  - Ahora: `"Ya existe una cuenta o solicitud con este correo"`

  Si el frontend hace matching de texto sobre ese mensaje (no debería, pero no lo verifiqué del
  lado de RN), este es el único lugar donde notaría el cambio. El rate limit (`RateLimitExceededException`
  → 429) no cambió ni de status ni de mensaje.

- **`UserAccountService.inviteStaff`: sin cambio de contrato.** Sigue devolviendo `UserId` (200/201
  según lo mapee el controller de admin, que no toqué) tanto si el correo se manda bien como si
  falla — antes, un fallo de SMTP hacía que la excepción escapara DENTRO de la transacción, lo cual
  en los hechos revertía todo (usuario + credencial) y el admin veía un 503
  (`EnvioEmailFallidoException` → `SERVICE_UNAVAILABLE` en `GlobalExceptionHandler`). Con el
  arreglo, ese mismo escenario ahora responde con éxito (la invitación sí se creó) y el fallo de
  correo queda solo en el log del servidor. **Esto sí es un cambio de comportamiento observable**:
  antes de mi cambio, un SMTP caído hacía que `inviteStaff` fallara con 503; después de mi cambio,
  `inviteStaff` siempre tiene éxito si el usuario es válido, independientemente de si el correo
  sale o no. Lo considero una mejora (el defecto original, C-11, es justamente que el correo no
  debería poder tumbar el alta), pero es una diferencia de contrato real que hay que poder
  explicarle a un admin que hoy quizás interpreta el 503 como señal de que la invitación no se
  hizo.

## Para la bitácora

```
### E-XX: SMTP dentro de @Transactional revertía altas de staff completas ante un fallo de correo

**Síntoma:** un admin invitando staff nuevo recibía 503 ("No pudimos enviar el correo. Intenta de
nuevo en unos minutos.") y el usuario invitado NO quedaba creado (rollback completo), aunque el
alta en sí (usuario + credencial) no tenía nada de malo. Con un SMTP lento, además, la conexión de
Hikari quedaba retenida hasta 15s por intento, con riesgo de agotar el pool para toda la API.

**Causa real:** `UserAccountService.inviteStaff` llamaba a `EnviarEmailPort.enviarInvitacionStaff`
(una llamada de red a un servidor SMTP) DENTRO del método `@Transactional`. Cualquier fallo de esa
llamada (o solo la demora) se propagaba con la transacción todavía abierta.

**Solución:** el envío se difiere a un `TransactionSynchronization.afterCommit()` (mismo patrón que
`MensajeService.publicarDespuesDelCommit`, chat). El alta (usuario + credencial) queda confirmada
en Postgres ANTES de intentar el correo; si el correo falla, se loguea en ERROR y no se propaga —
el invitado ya tiene una credencial real y puede recuperar acceso por "olvidé mi contraseña" si
nunca le llega el correo con la contraseña temporal.

**Cómo evitar que vuelva a pasar:** cualquier llamada a un puerto `out` que hable con un sistema
externo lento (SMTP, un proveedor OIDC, IA) tiene que revisarse contra la regla de C-1/CLAUDE.MD §7:
"ninguna llamada a un puerto externo corre dentro de `@Transactional`". Buscar `enviar` + `Port`
dentro de métodos `@Transactional` es un grep rápido para auditar el resto del código.
```

```
### E-XX: rate limit de alta por IP con check-then-act (Postgres) y token de verificación
### desperdiciado en intentos que iban a fallar igual

**Síntoma:** en teoría, ráfagas de solicitudes concurrentes desde la misma IP podían superar el
límite documentado de 60/hora; y alguien que reintentaba un alta con un correo que ya tenía cuenta
se quedaba sin poder reintentar con OTRO correo sin volver a verificar su casilla de cero (el token
de verificación, de un solo uso, ya se había consumido en el intento fallido).

**Causa real:** `AccountRequestService.rejectIfRateLimitExceeded` hacía un `SELECT COUNT` contra
Postgres y DESPUÉS insertaba — dos sentencias separadas, sin atomicidad entre ellas. Por separado,
`submit()` consumía `verificationToken` (GETDEL en Redis) ANTES de intentar el `INSERT`, así que
cualquier fallo posterior (típicamente, el `UNIQUE` de `usuarios.email`) dejaba el token perdido
sin haber servido para nada.

**Solución:** el límite por IP pasó a `LimitarSolicitudesResetPort.registrarIntento` (Redis, `INCR`
atómico) — el mismo puerto que ya usan `VerificacionEmailService` y `ConsultaEmailService`. Se
agregó un chequeo explícito de "¿el correo ya existe?" (`loadUserPort.byEmail` +
`loadAccountRequestPort.existePorEmail`) ANTES de consumir el token de verificación.

**Cómo evitar que vuelva a pasar:** cualquier límite de tasa nuevo en `users` debería apoyarse en
`LimitarSolicitudesResetPort` (o el equivalente de otro módulo) desde el principio, no en un
`COUNT` de Postgres — ya hay tres usos del mismo puerto en este módulo como referencia. Para
recursos de un solo uso (tokens, códigos), la regla general es: validar/chequear lo más posible
ANTES de consumir, y consumir lo más tarde posible dentro del flujo.
```

```
### E-XX: doble confirmación de alta social (misma identidad) recibía 409 genérico en vez de
### tratarse como éxito idempotente

**Síntoma:** dos llamadas casi simultáneas a `POST /auth/social/complete` para la MISMA identidad
de Google/Apple/Facebook (dos pestañas, un reintento de red, un doble tap en "Confirmar") hacían
que la segunda recibiera un 409 genérico ("La operacion entra en conflicto con datos que ya
existen") en vez de la misma respuesta de éxito que ya recibe la primera.

**Causa real:** desde D-65, cada llamada a `POST /auth/social` para una identidad nueva genera un
token de continuación INDEPENDIENTE (no hay memoria de tokens anteriores para la misma identidad).
Si dos de esos tokens se confirman casi al mismo tiempo, ambos intentan crear la misma
`AccountRequest`/`User`; el segundo choca contra el `UNIQUE` de `usuarios.email` y esa
`DataIntegrityViolationException` no estaba capturada en `CompletarRegistroSocialService`.

**Solución:** se captura la `DataIntegrityViolationException` alrededor de la llamada a `submit()`
y, si existe una `AccountRequest` pendiente para la MISMA identidad social
(`loadAccountRequestPort.porOrigenSocial`), se devuelve su id en vez de dejar escapar el error —
mismo criterio que ya aplica `vincularIdentidadSocial` ("el doble tap del cliente móvil no es un
error"). Si el conflicto no es de la misma identidad, se relanza el error original.

**Cómo evitar que vuelva a pasar:** cualquier caso de uso que pueda recibirse dos veces por la
misma "cosa lógica" desde flujos separados por un paso intermedio en Redis (token de continuación,
OTP, etc.) tiene que decidir explícitamente qué hacer con el segundo — no asumir que "nunca va a
pasar". El criterio de este módulo: si hay una forma barata de detectar "esto ya se hizo" (una
consulta de lectura, un `UNIQUE` de la base), tratar el segundo intento como éxito idempotente, no
como error.
```

## Para el registro de decisiones

```
### D-XX: fallo de envío de correo nunca revierte una escritura ya confirmada; se prefiere
### "olvidé mi contraseña" como red de recuperación en vez de un reintento de envío dedicado

Contexto: C-11 encontró que `inviteStaff` mandaba el correo de invitación DENTRO de la transacción
que crea el usuario, así que un SMTP caído revertía el alta entera.

Decisión: separar SIEMPRE "la escritura que importa" (usuario + credencial) del envío del aviso, y
que un fallo del segundo nunca deshaga ni bloquee el primero. Para la recuperación, en vez de
construir un mecanismo de reintento de ENVÍO dedicado (cola, endpoint de "reenviar invitación"), se
apoya en el flujo ya existente de "olvidé mi contraseña": como la invitación ya deja creada una
`Credencial` real (aunque desconocida para el invitado), esa persona siempre puede recuperar acceso
por ese camino si el correo con la contraseña temporal nunca llega.

Pendiente de confirmar con el dueño del producto: si esto es aceptable como UX (el invitado no se
entera de que su correo falló, salvo que intente entrar y no pueda) o si en algún momento hace
falta que el admin vea, en el panel, qué invitaciones no llegaron a mandarse.
```

```
### D-XX: los límites de tasa nuevos en `users` van sobre LimitarSolicitudesResetPort (Redis),
### no sobre un COUNT de Postgres

Contexto: C-16 encontró que el límite de 60 solicitudes/hora por IP en el alta pública se
implementaba con un `SELECT COUNT` de Postgres, check-then-act, sin atomicidad frente a envíos
concurrentes.

Decisión: reutilizar `LimitarSolicitudesResetPort` (ya usado por `VerificacionEmailService` y

("Reset") ya no describe bien su uso real (van tres consumidores con propósitos distintos); se dejó
así por ahora para no ampliar el alcance de un hallazgo "baja" — se sugiere, como limpieza
separada, renombrarlo a algo como `LimitarIntentosPort` cuando se toque ese archivo por otro motivo.
```
